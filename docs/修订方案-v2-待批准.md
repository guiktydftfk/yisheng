## 1. 实测基线（先摆事实，再谈改法）

我用临时库（未触碰 `data/yisheng.db`）复核了 GPT 指出的问题。**四项全部复现，另发现一个它没提到的 500 bug。**

| 编号 | 问题 | 我的实测结果 | GPT 说对了吗 |
|---|---|---|---|
| P0-1 | metadata 不是原始字符串 | 传 `"普通字符串"` → **422**；传 `'{"a":1}'` 文本 → **422**；传对象 → 201；库内存 `{"k": "v"}`（JSON 文本）；读回被还原成 dict | ✅ 完全正确 |
| P0-2 | AUTOINCREMENT 描述夸大 | 见下方专项实测 | ✅ 正确 |
| P0-3 | 读取时不校验哈希 | 直接改库后 `GET` 返回被篡改的 content，**旧 sha256 原样返回，无任何异常** | ✅ 完全正确 |
| P0-4 | `BUSY → True` 不可靠 | 代码确为 `if "locked"/"busy" in msg: return True`；且每次 `/health` 都做一次真实写入 | ✅ 正确 |
| **D4+** | **超范围游标会 500**（GPT 未提，我实测发现） | `s:9223372036854775807` → 200；`s:9223372036854775808` → **`OverflowError: Python int too large to convert to SQLite INTEGER`** → 真实服务下是 **HTTP 500** | ⚠️ GPT 只要求"新增上限检查"，未指出当前已是 500 |

### 1.1 AUTOINCREMENT 专项实测（决定 P0-2 的措辞）

```
连续插入 a,b,c            -> seq = [1, 2, 3],  sqlite_sequence = 3
BEGIN; INSERT 'rollback'  -> 事务内 seq = 4
ROLLBACK                  -> 行数 3,  sqlite_sequence 回退为 3
再 INSERT 'after-rollback'-> seq = 4          ← 回滚的序号被复用
DELETE seq=3; INSERT      -> seq = 5          ← 已提交用过的序号不复用
```

**结论（与 GPT 的修正一致）：**
- 已提交记录用过的序号，后续**不会**重新使用 ✅
- **回滚**事务占用的序号**会**被复用 ✅
- 允许出现空洞 ✅
- 不能保证连续 ✅

我们现有文档里「绝不复用、回滚后也不回退」的表述是**错的**，必须改。

### 1.2 物理表专项实测（决定 D2 的措辞）

```
sqlite_master 中的表：['experiences', 'schema_version', 'sqlite_sequence']
```

**物理上确实是 3 张表**——`sqlite_sequence` 由 `AUTOINCREMENT` 自动创建。GPT 的 D2 意见正确：
契约只能声称「**应用自定义表**恰好为 `{experiences, schema_version}`」，不能声称整个库只有两张物理表。

### 1.3 synchronous 专项实测（决定 D1 的建议）

WAL 模式，1500 条，本机（D 盘）实测：

| 场景 | `synchronous=NORMAL` | `synchronous=FULL` | 差距 |
|---|---|---|---|
| 单条自动提交（≈真实 API 写入路径） | 22,198 条/秒 | **298 条/秒** | **约 74 倍** |
| 单事务批量 1500 条（≈导入路径） | 1,024,450 条/秒 | 328,666 条/秒 | 约 3 倍 |

单条提交下 FULL 的代价是每次 `commit` 都 fsync WAL —— 折算约 **3.4 ms/条**。

**这个数字是 D1 建议的关键**（见 §6 E3）。

## 2. A. 修订计划

### P0-1　metadata 改为真正的原始字符串

**现状**：`ObserveRequest.metadata: dict | None` + validator 里 `json.dumps`；`Experience.metadata` 用 `mode="before"` 的 validator 做 `json.loads`。等于把「字符串存储」做成了「JSON 对象 API」。

**改法**：

| 位置 | 改动 |
|---|---|
| `models/experience.py::ObserveRequest` | `metadata: str \| None`；删除 `_metadata_kept_raw` 里所有 `json.dumps`；**不加任何结构校验**（不解析、不判断是否合法 JSON） |
| `models/experience.py::Experience` | `metadata: str \| None`；删除 `_metadata_from_raw` 的 `json.loads`，直接原样返回 |
| `services/experience_service.py` | 签名保持 `metadata: str \| None`，直接透传（本来就没解析，无需改逻辑，仅改类型） |
| `db/repository.py` | 不变（本来就是 TEXT 原样写入） |
| `db/schema.sql` | 列注释补一句「客户端提交的原始字符串，服务端不解析」 |

**对已有数据的影响**：`data/yisheng.db` 现有记录的 `metadata` 列本来就是 TEXT，里面是 JSON 文本。
改为 `str` 返回后，这些记录会返回 `'{"k": "v"}'` 这个**字符串**，而不是 `{"k": "v"}` 对象。
**数据不丢、不用迁移**，但客户端解读方式变了 —— 这是契约变更，列入 §4。

**明确不做**：不提供"兼容两种形态"的自动识别（那本身就是解析与猜测，违反本条契约的本意）。

### P0-3　让 `content_sha256` 真正起作用（读取时校验）

**现状**：只写不验。等于一个只被记录、从不被使用的字段。

**改法**：

1. `content_sha256` 只针对 `content` 字段（在 docstring 与文档中写死这一点）
2. 新增 `errors.py::DataIntegrityError`
3. **读取路径重新计算并比对**：
   - `GET /experiences/{id}`（详情）→ 必须校验
   - `GET /experiences`（列表）→ 也必须校验（否则"发现篡改"可以通过翻页绕过）
   - 校验在 `services/experience_service.py` 里做，不在路由层
4. 不一致时抛 `DataIntegrityError` → 全局处理器映射为 **`500` + `{"error": "data_integrity_error"}`**
   （选 500 而不是 409：这是**服务端数据损坏**，不是客户端冲突）
5. 错误体里带上 `sequence`/`id`，便于定位是哪条坏了；**不回显被篡改的内容**

**文档必须写清的能力边界**：

> SHA-256 能检测「内容与摘要不一致」。
> 它**不能阻止**数据库被修改；若攻击者同时修改 `content` 与 `content_sha256`，普通 SHA-256 **无法**证明未被篡改。
> 本阶段不引入 HMAC、签名、密钥管理。
> **不声称本系统已具备完整防篡改能力。**

**性能代价（需要你知晓）**：列表页每条都要算一次哈希。最坏情况一页 100 条 × 100,000 字符
→ 10 MB 数据计算 SHA-256，实测量级约 **20–40 ms**。这在 Phase 1 可接受，但若你选 §6 E4 的方案 B（列表不返回全文），
列表校验可改为「只校验摘要字段所属的 content」，成本不变（仍要读）。

> ⚠️ 若你希望**列表不校验、只在详情校验**，请明确告知——那会留下"篡改可通过分页被静默带出"的缺口，我不建议。

### P0-4　重新设计 `/health` 的可写性判断

**现状问题（两条）**：
1. `BUSY/locked → True`：忙碌只说明拿不到锁，**不能证明可写**。
2. 每次 `/health` 都做真实写入再回滚：会给正常写入制造写锁竞争。

**改法（推荐方案 H1，需批准，列入 §4）**：

```
GET /health                → 只做无副作用的检查，绝不写入
GET /health?probe=write    → 才执行一次事务内真实写入探测
```

`/health` 响应结构调整为：

```json
{
  "status": "ok",
  "schema_version": 1,
  "db_path": "...",
  "db_writable": true,                  // true / false / null（null = 无法判断）
  "db_write_status": "writable"          // writable | readonly | busy | unknown | error
}
```

判定规则：

| 情形 | `db_write_status` | `db_writable` |
|---|---|---|
| `probe=write` 且真实写入成功 | `writable` | `true` |
| 明确 `readonly` / 只读连接 / `PRAGMA query_only=1` | `readonly` | `false` |
| 拿到锁失败（BUSY/locked） | `busy` | **`null`**（绝不报 true） |
| 其他数据库错误 | `error` | `false` |
| 未指定 `probe=write`（默认） | `unknown` | **`null`** |

**关键取舍**：默认 `/health` **不再声称可写**（返回 `null` + `unknown`）。
理由是"不写入就无法证明可写"，把 `unknown` 说成 `true` 正是 GPT 指出的伪装。
真正需要确认可写时，显式用 `?probe=write`。

**备选方案 H2（不动响应结构）**：保留 `db_writable: bool`，语义收紧为
「仅在能确证可写时 true；busy/无法判断一律 false」，默认不做写入探测。
缺点：把"未知"折叠成 `false`，语义仍有损，且会让目标机验收项 `db_writable: true` 永远不成立。

> 需要你在 §6 E1 选 H1 还是 H2。

### D4　Cursor 的边界 + 整数上限

**改法**：

1. 文档明确：Base64 **只用于隐藏内部格式，不是加密**；游标是**不透明 API 参数，不是安全凭证**；

2. **代码修复（真 bug）**：`decode_cursor` 增加上界检查

```python
SQLITE_MAX_INT = 2**63 - 1     # 9223372036854775807

value = int(tail)
if value < 1 or value > SQLITE_MAX_INT:
    raise InvalidCursorError("cursor 序号超出 SQLite INTEGER 范围")
```

3. 新增测试：`s:0`→400、`s:2^63-1`→200（空页）、`s:2^63`→400、`s:10^30`→400。

### 5.2 分层标记（GPT 要求区分四层）

用 pytest marker 标注，避免把不同层的证据混为一谈：

| marker | 含义 | 例 |
|---|---|---|
| `@pytest.mark.api` | HTTP 层保护/行为 | PUT→405、400/422 区分 |
| `@pytest.mark.repository` | 仓储层约束 | 不暴露 update/delete、SQL 只在 repo |
| `@pytest.mark.sqlite` | SQLite 真实行为 | AUTOINCREMENT 回滚、WAL、并发 |
| `@pytest.mark.integrity` | 数据完整性检测 | 篡改后读取报错 |
| `@pytest.mark.contract` | 七条验收 | —— |

**静态检查不再充当运行时证据**：现有 4 条静态测试保留，但每条都标注
「这是静态补充，对应行为另有运行时测试」；并在文档里显式说明。

## 6. E. 待你决策的设计选择

> 请只回这里的选择编号即可，例如「E1 选 H1；E2 选 B；E3 选 FULL」。

### E1　`/health` 方案（对应 P0-4）

- **H1（推荐）**：响应加三态 + `db_write_status`；默认不写；`?probe=write` 才真探测。
  *代价*：C2 破坏性变更；目标机验收项要改成「`?probe=write` 时 `db_writable=true`」。

  *代价*：语义把"未知"说成"不可写"，仍是失真；不推荐。

### E2　列表返回 content（对应 §四）

| 方案 | 做法 | 最坏单页负载 | 影响 |
|---|---|---|---|
| **A1** | 保留完整 content，`MAX_PAGE_LIMIT` 100→**20** | 20×100k = 2M 字符（UTF-8 最坏 ~8MB） | 无 API 结构变更，仅常量变化；分页次数变多 |
| **A2** | 保留完整 content，加**字节预算**保护（估算超限则 422 或自动降 limit） | 受预算约束 | 逻辑变复杂，但 API 兼容 |
| **B（推荐）** | 列表只返回轻量字段（id/sequence/两个时间/source/content_length/content_preview/hash），完整 content 仅 `GET /{id}` 返回 | ~100×300B ≈ 30KB | ⚠️ **破坏性**：列表不再返回 content；且 preview 需要你批准（属于截断，不是摘要） |

> 我推荐 **B**：它把"一页 40MB"这个结构性风险一次性消掉，也让 P0-3 的校验成本可控
> （列表只校验其摘要字段所需的 content 读取——仍需读全文算哈希，但不再进入响应）。
> 若你想最小改动，选 **A1**。
> 注意：B 与第 86 轮「列表返回完整 content」的旧决定冲突，属于**契约回退**，必须你明确批准。

### E3　`synchronous` 策略（对应 D1）

实测：单条提交下 FULL 比 NORMAL **慢约 74 倍**（298 vs 22,198 条/秒，即 3.4ms/条）。

| 方案 | 应用崩溃 | OS 崩溃/断电 | 单条写吞吐 |
|---|---|---|---|
| `NORMAL`（现状） | 安全 | **可能丢失最近若干已提交事务**（库不损坏） | 22,198 条/秒 |
| `FULL` | 安全 | 已提交即落盘 | 298 条/秒 |
| **推荐：FULL（写连接）+ NORMAL（读连接）** | 安全 | 已提交即落盘 | 298 条/秒（3.4ms/条，对人类节奏的经历流足够） |

**推荐理由**：
1. 项目目标是"长期保存原始经历"，**丢一段已提交的经历比慢 3.4ms 严重得多**；
2. 298 条/秒 = 每条 3.4ms，对"经历流"这种人类节奏的数据源绰绰有余；
3. 真正需要吞吐的是**批量导入**，而批量导入应放单事务——实测 FULL 单事务仍有 328,666 条/秒，损失可接受。

**若选 NORMAL**，我会在文档里明确写「断电可能丢失最后数秒已提交经历」，并把它列入风险清单，不隐瞒。

### E4　哈希校验范围（对应 P0-3）

- **V2**：只在详情校验。代价：列表会把被篡改内容返回出去且不报错——留下缺口。

### E5　哈希校验代码位置
