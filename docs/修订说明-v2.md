## 2. 每个问题的修复方式

### P0-1　metadata 改为真正的原始字符串

| 改动 | 内容 |
|---|---|
| `ObserveRequest.metadata` | `dict[str, Any] \| None` → **`str \| None`** |
| 写入路径 | 删除 `json.dumps()`；原样透传给仓储层 |
| `Experience.metadata` | `Any` → **`str \| None`** |
| 读取路径 | 删除 `json.loads()`；原样返回 |
| 结构校验 | **不做**。不检查是否合法 JSON、不检查嵌套 —— 只要它是字符串 |
| 对象输入 | 422（提交对象意味着让服务端解析，违反契约本意） |

**对已有数据**：`metadata` 列本来就是 TEXT。若有历史记录存的是 JSON 文本，改后返回该**字符串**（不再变对象）。
**不丢数据、无需迁移**，但客户端解读方式变化 —— 属破坏性契约变更 C1（已批准）。

**测试证据**：`tests/test_metadata_raw.py`（8 项），含"库内值与提交值逐字一致"（直接 `SELECT` 比对）。

---

### P0-2　修正 AUTOINCREMENT 的契约表述

代码本就正确（`INTEGER PRIMARY KEY AUTOINCREMENT`），修正的是**注释与文档**：

```
✅ 已提交记录用过的序号，后续提交不会重新使用
✅ 允许出现序号空洞
❌ 回滚事务占用的序号可能被复用（sqlite_sequence 随事务回滚恢复）
❌ 不保证序号连续
```

`sequence` 只承担内部排序与分页；永久身份由 UUID v4 承担。

**实测记录**（本机 SQLite 3.45.3）：

```
插入 a,b,c        → seq [1,2,3]，sqlite_sequence = 3
BEGIN + 插入      → seq 4
ROLLBACK          → sqlite_sequence 回到 3，该行不存在
再插入            → seq 4      ← 回滚序号被复用
DELETE seq=3 后插 → seq 5      ← 已提交序号不复用
```

**测试证据**：`tests/test_sequence_autoincrement.py`（9 项），其中断言的是"**允许**复用/允许空洞"，
而不是"必须复用/必须连续"——避免把实现细节写成契约。

---

### P0-3　让 `content_sha256` 真正起作用

| 改动 | 内容 |
|---|---|
| 哈希范围 | 明确：**只针对 `content`** |
| 读取校验 | 详情与**列表都校验**（E4-V1）；不一致 → `DataIntegrityError` |
| 错误映射 | **500 `data_integrity_error`**，附带 `sequence` 与 `id`，**不回显被篡改内容** |
| 代码位置 | 校验在 `services/experience_service.py`（E5-R1），仓储层保持纯数据访问 |

**能力边界（写入文档、并用测试钉死）**：

> SHA-256 能检测「内容与摘要不一致」，**不能阻止**数据库被修改。
> 若攻击者同时改写 `content` 与 `content_sha256`，普通 SHA-256 **无法**证明未被篡改。
> 本阶段不引入 HMAC / 签名 / 密钥管理；**不声称已具备完整防篡改能力**。

**测试证据**：`tests/test_integrity.py`（6 项），含一条**刻意断言"检测不到"**的
`test_simultaneous_tamper_is_NOT_detectable`，防止以后有人把"检测不一致"说成"完整防篡改"。

**性能代价**：列表每条都要算哈希。实测 `limit=100 × 100,000 字符` 的最坏页约 20–40ms —— 可接受。

### P0-4　重新设计 `/health` 的可写性判断（方案 H1）

| 改动 | 内容 |
|---|---|
| 默认行为 | **不执行任何写入**；`db_write_status="unknown"`、`db_writable=null` |

### D1　`synchronous = FULL`（可靠性优先）

| 方案 | 应用崩溃 | OS 崩溃/断电 | 单条提交吞吐（实测） |
|---|---|---|---|
| NORMAL | 安全 | **可能丢失最近已提交事务**（库不损坏） | 22,198 条/秒 |
| **FULL（已采纳）** | 安全 | 已提交即落盘 | **298 条/秒**（约 +3.4ms/条） |
| 单事务批量（对照） | — | — | FULL 仍有 328,666 条/秒 |

采纳理由：丢一段已提交经历比慢 3.4ms 严重；298 条/秒对"经历流"这种人类节奏的数据源足够；
真正需要吞吐的是批量导入，应放单事务。

**代码**：`config.SYNCHRONOUS_MODE = "FULL"`，`db/connection.py` 每条连接显式设置。
`synchronous` 只影响写操作，读连接设 FULL 无额外成本。

## 4. 数据库 Schema 最终版本

**无结构变更**（无新增表、无新增列、无类型变更）。仅注释更新：

```sql
-- 契约 3：内部序号。AUTOINCREMENT 的真实保证（勿夸大）：
--   ✅ 已提交记录用过的序号，后续提交不会重新使用
--   ✅ 允许出现序号空洞
--   ❌ 回滚事务占用的序号可能被复用（sqlite_sequence 随事务回滚而恢复）
--   ❌ 不保证序号连续
-- 因此 sequence 只承担内部排序与分页职责；永久身份由 id(UUID v4) 承担。
-- 另注：本表会令 SQLite 自动创建内部表 sqlite_sequence，它不属于应用表集合。
CREATE TABLE IF NOT EXISTS experiences (
    sequence       INTEGER PRIMARY KEY AUTOINCREMENT,
    id             TEXT    NOT NULL UNIQUE,
    recorded_at    TEXT    NOT NULL,
    occurred_at    TEXT,
    content        TEXT    NOT NULL,
    source         TEXT,
    context        TEXT,
    outcome        TEXT,
    -- 客户端提交的**原始字符串**：服务端不解析、不校验内部结构、不建索引。
    metadata       TEXT,
    -- 仅针对 content 的 SHA-256。能检测不一致，不能阻止修改；
    -- 若同时改写 content 与 sha256，普通 SHA-256 无法识别。
    content_sha256 TEXT    NOT NULL,
    CHECK (length(content) > 0),
    CHECK (recorded_at IS NOT NULL)
);

CREATE INDEX IF NOT EXISTS idx_exp_sequence_desc ON experiences (sequence DESC);
CREATE INDEX IF NOT EXISTS idx_exp_recorded_at   ON experiences (recorded_at);

CREATE TABLE IF NOT EXISTS schema_version (
    version    INTEGER NOT NULL PRIMARY KEY,
    applied_at TEXT    NOT NULL
);
```

**应用自定义表集合**：`{experiences, schema_version}`
**物理表**：上述两张 + SQLite 内部表 `sqlite_sequence`（`AUTOINCREMENT` 自动创建，不属应用表集合）
**结构版本**：`schema_version = 1`（未变）

## 5. 四个 API 的最终契约

**端点数固定 4 个**，全部仅监听 `127.0.0.1`。

### 5.1 `POST /observe` — 记录一条经历

请求：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `content` | string | ✅ | 1..100,000 **字符**（按字符数，非字节），不能为纯空白 |
| `source` | string | — | ≤200 |
| `context` | string | — | ≤2000 |
| `outcome` | string | — | ≤2000 |
| `occurred_at` | string(ISO8601) | — | **必须带时区**，服务端归一化为 UTC |
| `metadata` | **string** | — | 任意字符串；**不解析、不校验结构**；传对象 → 422 |

额外字段（如 `recorded_at`）→ **422**（`extra="forbid"`）。

成功 `201`：

```json
{"id":"<uuid v4>","sequence":1,"recorded_at":"2026-11-07T13:17:05.403612+00:00","occurred_at":null}
```

### 5.2 `GET /experiences` — 列表（摘要）

| 参数 | 默认 | 说明 |
|---|---|---|
| `limit` | 20 | 1..100，越界 → 422 `invalid_limit` |
| `cursor` | — | 不透明字符串；合法范围 `1..2^63-1`，非法 → 400 `invalid_cursor` |

响应 `200`：

```json
{
  "items": [{
    "id": "…", "sequence": 1,
    "recorded_at": "…", "occurred_at": null,
    "source": "…",
    "content_length": 12345,
    "content_preview": "前 200 字符…",
    "content_truncated": true,
    "content_sha256": "…"
  }],
  "next_cursor": "opaque-or-null",
  "has_more": false
}
```

排序 `ORDER BY sequence DESC`；**不含 `content` 全文**。
若任一条内容与哈希不一致 → **500 `data_integrity_error`**。

### 5.3 `GET /experiences/{id}` — 详情

响应 `200`：完整对象（含 `content`、`metadata` 原文、`content_sha256`）。

| 情况 | 状态码 | error |
|---|---|---|
| 不存在 | 404 | `not_found` |
| 非合法 UUID | 400 | `bad_request` |
| 内容与哈希不一致 | **500** | **`data_integrity_error`** |

### 5.4 `GET /health` — 健康检查

| 参数 | 说明 |
|---|---|
| `probe` | 仅 `write` 触发一次真实写入探测；其他值按默认（不探测） |

响应 `200`：

```json
{"status":"ok","schema_version":1,"db_path":"…","db_writable":null,"db_write_status":"unknown"}
```

| `db_write_status` | `db_writable` | 含义 |
|---|---|---|
| `writable` | `true` | 已确证可写（仅 `probe=write` 成功时） |
| `readonly` | `false` | 只读库 / `query_only=1` |
| `busy` | `null` | 拿不到写锁（**不判定为可写或不可写**） |
| `unknown` | `null` | 默认未探测 |
| `error` | `false` | 其他数据库错误 |

### 5.5 明确不实现

| 请求 | 结果 |
|---|---|
| `PUT` / `PATCH` / `DELETE /experiences/{id}` | **405** |
| 任何搜索 / 语义 / 关联 / 摘要 / 反思 / 信念端点 | 不存在 |
| 任何认知类字段或表 | 不存在 |

### 5.6 错误响应统一格式

